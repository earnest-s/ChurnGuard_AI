**Suggested layout**

1. One-line problem statement (Telco customer churn, binary classification, churn = positive class).
2. Table with the two rows printed by `train.py`:

   ```
   model                             cv_f1_mean  cv_f1_std  holdout_f1
   Baseline LogisticRegression       <x>         <x>        <x>
   AutoML winner (<EstimatorName>)   <x>         <x>        <x>
   ```

   Include the `AutoML vs baseline holdout F1: +0.xxxx` line.
3. Screenshot of the terminal block `3. AutoML model comparison` (it shows the
   candidate models and the winner).
4. Short paragraph: *metric choice*. F1 is the primary metric because the classes
   are imbalanced (churn rate `0.265`) and a false negative (a customer who churns
   unnoticed) costs more than a wasted retention offer. Report precision/recall
   alongside F1 rather than accuracy alone.

**Critical evaluation paragraph (paste and adapt)**

> The model was evaluated on a stratified 80/20 hold-out split (`random_state=42`)
> with 5-fold stratified cross-validation on the training partition only. All
> preprocessing (imputation, scaling, one-hot encoding) is fitted inside the
> scikit-learn pipeline, so no information from the hold-out set leaks into
> training. `customerID` was dropped as an identifier, and the 11 rows with a blank
> `TotalCharges` were removed. `TotalCharges` is almost a linear function of
> `tenure x MonthlyCharges` (Pearson r = 0.999), which is redundancy rather than
> target leakage, because the value is known before the prediction is made; keeping
> it was a deliberate decision and the SHAP plots show how it shares credit with
> `tenure`. A fairness slice on `gender` and `SeniorCitizen` is printed by the same
> script; the per-group recall values are within <fill in> points of each other.

**What NOT to claim**

- Do not write "eliminated leakage" as a slogan: point at the computed checks
  (`leakage_checks` in `/model-info`).
- Do not present the PyCaret hold-out F1 and the scikit-learn hold-out F1 as the
  same number: they use different random splits (`pycaret_holdout_f1` vs `f1` in
  the metadata).

## Page 2 - Explainable AI

**Figures (all produced by `python train.py`)**

| File | What it shows | Caption suggestion |
| --- | --- | --- |
| `shap_summary_bar.png` | mean absolute SHAP value per feature (global importance) | "Global feature importance measured with SHAP on the hold-out set; `Contract`, `tenure` and `TotalCharges` dominate." |
| `shap_beeswarm.png` | direction + spread of every feature's effect | "SHAP beeswarm: month-to-month contracts and low tenure push predictions toward churn, long tenure pushes away from it." |
| `shap_waterfall_high_risk.png` | single-customer explanation | "Local explanation of the highest-risk customer: how each feature value moves the prediction away from the base rate." |

**Method paragraph**

> Explanations use SHAP (`TreeExplainer` for tree-based winners, `LinearExplainer`
> for logistic regression) on the exact pipeline that serves predictions, so the
> attribution matches production behaviour. For one-hot encoded categorical
> variables the per-category SHAP values are summed back onto the original column
> (`Contract_Month-to-month` + `Contract_One year` -> `Contract`), which is what the
> API returns in `feature_importance`. Global importance is the mean absolute SHAP
> value over 200 hold-out rows; local importance is the signed contribution for the
> single request.

**GUI paragraph**

> `POST /predict` returns `feature_importance` (normalised absolute SHAP values),
> the three signed `top_factors`, and a generated English `explanation`. The React
> front-end renders the ranking as a bar chart, so a retention agent can see *why*
> a customer is flagged instead of only the score.

**Honesty note worth one sentence**

> SHAP values explain the model, not causality: they show which inputs the model
> relied on for this prediction, not what would happen to the customer if the
> feature were changed.

**Caption**

> The CI job installs `requirements-dev.txt`, runs flake8 (fails the build on any
> style error) and runs the pytest suite (22 tests covering the response contract,
> input validation, the retrain endpoint and the SHAP serving path) before the
> deploy job is allowed to start. Deployment builds a multi-stage image: stage 1
> installs pinned dependencies into a virtualenv with the build toolchain, stage 2
> copies only that virtualenv and the application code, runs as an unprivileged
> user, and exposes a `HEALTHCHECK` that Azure uses for container monitoring.

**Things a reviewer may probe - be ready**

- *Why is PyCaret not in the Docker image?* The AutoML search is a training-time
  concern. The winning estimator is exported as a plain scikit-learn pipeline, so
  the runtime image needs only scikit-learn + SHAP (~10x smaller, faster cold start,
  smaller attack surface). This is the standard "search wide, ship narrow" pattern.
- *Why is the model artifact committed?* So a fresh clone and a fresh container can
  serve the trained model without a GPU-scale training step. Retraining is
  `python train.py`, and the artifact is the thing that gets reviewed/versioned.
- *The "Retrain" button.* With the AutoML artifact loaded, `/retrain` returns 409 and
  explains that retraining happens offline via `train.py`. Training on the model's
  own predictions would be a feedback loop, so it is refused on purpose. The
  fallback baseline model still supports online retraining from the prediction log.
- *`support_calls`.* It is kept for backwards compatibility with the original
  front-end but is not part of the Telco dataset, so the AutoML model ignores it.
  The synthetic fallback model still uses it.
